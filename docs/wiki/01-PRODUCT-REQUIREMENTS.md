
# 01. 产品需求规格说明书 (PRD)

## 1. 项目背景与愿景

随着多 Agent 协同与多样化编码助手的普及，开发者在日常工作中经常面临两大割裂痛点：
1. **多终端切换割裂**：开发者在公司工位机（如 Windows/Linux）与个人笔记本（如 macOS）之间切换时，各编码助手的上下文无法漫游，换台电脑就“失忆”，导致重复提问与上下文断层。
2. **多助手生态割裂**：开发者往往同时使用 **OpenAI Codex**（桌面客户端/CLI）与 **WorkBuddy**（或者 Claude Code 等），在某个工具中探索出的深度代码方案、重构思路无法直接流转给另一个助手继续执行。

本项目旨在打造一个**开放式、多 Agent 跨设备会话聚合与双向同步中心（AIAssets）**。

---

## 2. 核心用户场景

### 场景 A：跨设备工作流无缝接续
- **描述**：开发者在办公室电脑（Windows）上与 Codex / WorkBuddy 进行了 20 轮对话，定位并修复了一个复杂的 Vue/Node 架构 Bug。下班回家后，在 MacBook 上打开对应工程，会话记录已经自动同步就绪，可以直接敲回车继续提问“*把刚才修好的接口补一下单元测试*”。

### 场景 B：跨助手会话继承 (Codex ➡️ WorkBuddy / 反向)
- **描述**：在 Codex 中完成了长上下文的代码规划与方案评审后，一键将当前完整推理与对话流注入到 WorkBuddy 本地工程中，WorkBuddy 原生界面直接展示该会话，接续执行本地构建与复杂插件调用。

### 场景 C：集中可视化管理与审计
- **描述**：提供本地或云端 Web 控制台，可视化查阅所有机器、所有 Agent 的历史会话树，支持全文检索、Token 消耗统计、敏感凭据脱敏以及跨机器路径映射配置。

## 3. 功能需求矩阵

| 模块 | 功能项 | 优先级 | 详细说明 |
| :--- | :--- | :--- | :--- |
| **适配器内核** | Codex 会话提取与降噪 | **P0 (当前)** | 读取本地 JSONL，剥离系统注入提示词，保留用户输入、AI 答复与推理 |
| **适配器内核** | WorkBuddy 注入与写回 | **P0 (当前)** | 生成符合 WorkBuddy 规范的 JSONL，原子更新本地 SQLite sessions 表 |
| **适配器内核** | Pi 读取与注入 | **P0 (已完成)** | 读取 `~/.pi/agent/sessions` version 3 JSONL，按官方格式写回任意目标项目 |
| **同步引擎** | 本地跨助手直迁（免上云） | **P0 (已完成)** | 任意 Agent 会话可直接迁移到其他 Agent，无需先上传云端；云端仅作为跨设备通道 |
| **Web 控制台** | 统一会话资产库 | **P0 (已完成)** | 本地与云端按会话 ID 合并展示，状态标记：仅本地 / 已上云 / 仅云端；目标项目分组实时读取各 Agent 自己的数据库 |
| **路径映射** | 相对路径归一化 | **P0 (当前)** | 提取时将绝对路径转化为相对项目根目录的 Canonical Path |
| **路径映射** | 跨平台路径还原 | **P0 (当前)** | 根据目标设备的根目录与 OS（Win/Mac/Linux）动态重映射绝对路径 |
| **CLI 工具** | 命令行会话导出与同步 | **P0 (当前)** | 提供 `sync list`、`sync export`、`sync inject` 命令行交互 |
| **端云同步** | WebDAV / S3 云存储接入 | **P1 (下阶段)** | 会话加密后上传至指定云存储，多设备下拉合并 |
| **安全机制** | 本地端到端加解密 (E2EE) | **P1 (下阶段)** | 本地使用用户主密码通过 AES-256-GCM 加密后再上传云端 |
| **管理后台** | 可视化 Web 控制台 | **P2** | React / Fastify 架构，提供会话浏览、搜索与一键同步面板 |
| **权限系统** | 登录认证与多设备授权 | **P2** | 支持账号密码、OAuth、多设备 Token 颁发与撤销 |

## 4. 非功能性需求与设计原则

1. **绝对安全性 (Security First)**：
   - 绝不允许将未脱敏的凭据（如 API Key、Cookie、内网地址）明文上传。
   - 云存储必须强制支持端到端加密（E2EE），云端只能看到加密数据块（Zero-Knowledge）。
2. **零数据损坏保证 (Non-Destructive)**：
   - 注入本地客户端时，绝不破坏现有的未同步会话。遇冲突时采用“另存为副本分支”策略，禁止静默覆盖。
3. **低延迟与高流式吞吐 (Streaming I/O)**：
   - 本地 JSONL 往往包含数十兆的工具执行日志，必须采用流式逐行处理，禁止单次全量读入内存造成 OOM。
